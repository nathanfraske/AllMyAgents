# AllMyAgents v0.1.19-alpha.22

Released 2026-08-05.

## Purpose

This release hardens both Claude and Codex connections to the AllMyAgents control plane. Existing Overseers,
project managers, and managed workers retain the correct app role, tool-discovery rules, live topology, and
permission path after a vendor context compaction or resumed conversation. It also closes the upstream-routing
gap that could leave a managed child waiting on an operator-only prompt that its manager or Overseer never saw,
and makes every configured child purpose directly inspectable from the normal fleet views.

The journal, authentication, lazy-history, project lifecycle, remote testbed, team generation, and supervisor
hardening from the prior cuts remains fully logged in the earlier release ledgers. This document records only the
additional release delta.

## Durable provider-native app and role contracts

- Every Claude SDK query receives a compact AllMyAgents host contract through Claude Code’s supported preset
  system-prompt append. The app does not replace Claude Code’s own base prompt.
- The append is supplied again on every new or resumed invocation, so vendor conversation compaction cannot
  permanently summarize away the app’s tool discovery, role, or permission-routing rules.
- Claude-created internal subagents receive the same host boundary through the SDK’s subagent system append.
- The contract directs Claude to inspect live `mcp__allmyagents__` schemas, including through `ToolSearch`, before
  claiming an app capability is absent. It explicitly distinguishes AllMyAgents fleet and control-plane tools
  from similarly named Claude-native project/subagent tools.
- Codex receives the equivalent role-specific text through app-server's documented `developerInstructions`
  field on `thread/start` and `thread/resume`. The integration does not send an unsupported arbitrary field on
  `turn/start` and does not replace Codex's base instructions.
- The Codex adapter compares the exact live developer-instruction bytes before every accepted turn and rejoins
  an already-running thread only when they changed. A completed `contextCompaction` invalidates that equality
  cache, forcing the next turn to reassert the current app contract even if its text is unchanged.
- A newly allocated Codex thread is explicitly fenced until its first turn starts. App-server has not persisted
  a rollout during that short window, so a topology change cannot provoke an invalid early `thread/resume` and
  the resulting `no rollout found` failure.
- This closes the one-time-discovery weakness of relying only on `AGENTS.md`: current Codex documentation states
  that its project instruction chain is discovered once per run, while app-server explicitly supports updating
  developer instructions when a thread is resumed.
- Overseers are pointed first at `overseer_control`, fleet-wide `list_agents`/`peek_agent`, UI guidance,
  diagnostics, projects, teams, sessions, approvals, accounts, remote devices, pairing, audited elevation, and
  supervised restart operations.
- Project managers are reminded of the real child status, team, spawn, authority, approval, assignment, fleet,
  and bus surfaces. Managed children are reminded that a manager assignment is authorized work within the
  persisted grant and that a true block must be reported upstream.
- Existing Application Overseer sessions upgrade in place from capability contract v3 to v4. Their conversation,
  profile binding, session identity, and history remain intact while the live instructions are rematerialized.

## Compaction continuity without stale authority

- Instruction-cache invalidation is deliberately narrow: it forgets only the adapter's local equality memo so
  the current host contract is reasserted. It never deletes, restarts, replaces, or truncates the provider thread,
  the provider's compacted summary, the chat journal, or the agent's active assignment.
- Both vendors receive one shared continuity contract requiring the compacted state to retain the operator's
  active objective, project, current slice, scope, constraints, and acceptance criteria.
- The contract also preserves established decisions and invariants; completed work and its evidence; in-progress
  and prioritized remaining work; the exact next useful action; relevant files, worktrees, branches, commits,
  diffs, tests, and external identifiers; team assignments and pending integration; approvals, questions,
  blockers, failures, risks, and outstanding user input.
- Summaries must distinguish verified facts, tentative hypotheses, disproved leads, and unfinished work. A plan
  cannot be upgraded into a completed result, and a failing verification cannot be silently omitted.
- Codex receives a complete thread-scoped `compact_prompt`, because that setting replaces the vendor default
  rather than appending to it. The same contract is also present in its live developer instructions.
- Claude receives the contract in the per-query system append that is present when Claude Code performs its
  native compaction and again when the compacted conversation resumes. The app does not fabricate or replace
  Claude's summary; it gives the native compactor the state-retention requirements at its supported boundary.
- Live permissions, topology, and tool schemas remain separate from historical continuity. The summary retains
  what the agent was doing, while the host refreshes current authority instead of trusting a stale snapshot.

## Bounded live topology and manager operating discipline

- A manager's provider-native contract contains every durable team generation (up to the existing 32-team
  product bound), its active/stashed/inactive state, member/running/error counts, and a capped direct-child
  mapping of immutable agent id to name, provider, account, lifecycle, team, and last activity.
- A managed child receives its parent identity, all of that manager's bounded team states, and a same-team peer
  ID/name/status map. This is enough to coordinate without treating another team's stashed work as current.
- The Overseer receives a capped index of active/starting agents plus sessions with activity in the prior seven
  days. The index is limited to 48 agents, 24 projects, and 32 team rows; omitted counts are explicit.
- If the direct operator message names a known project, that project is prioritized in the bounded index even
  when its sessions are older. The Overseer is explicitly required to refresh the project and relevant
  manager/child state through live `status`, `list_agents`, and `peek_agent` calls before answering or mutating.
- Only hub-owned structural metadata enters this high-priority snapshot. Child messages, task prose, tool output,
  commands, and filesystem paths remain outside it, preventing a worker from promoting its own text into system
  or developer authority.
- Every project manager is reminded to use independent active-team capacity in parallel, avoid duplicate
  assignments, and explain intentionally unused capacity. A management cycle must dispatch, decide, inspect
  bounded evidence, integrate, or report one exact blocker rather than entering an idle holding pattern.
- Claude managers receive an explicit anti-meandering discipline: keep the critical path moving, avoid passive
  polling, integrate completions, and finish or escalate once the outcome is resolved.
- Codex managers receive the complementary stopping discipline: reproduce and rank suspected issues, discard
  benign noise, keep investigation/token use bounded, avoid opportunistic scope growth, and stop when the
  operator's acceptance criteria pass.

## Permission escalation without authority laundering

- A pending Claude or Codex tool request is summarized with the exact tool and a bounded command, file path, or
  requested permission profile, avoiding
  a generic “approval needed” alert that gives the upstream agent too little context to help.
- A capable direct manager receives the request through the existing manager child-approval channel and decides
  it with `decide_child_approval`; the hub still enforces direct-child scope and the manager’s live grant ceiling.
- If the direct manager cannot approve children, is stopped, is in error, or does not exist, the available
  Overseer receives a diagnostic alert containing the approval id, requester, action, and exact escalation reason.
- The fallback does not turn a system or teammate message into operator authority. The Overseer is told that only
  a direct operator turn may approve the request through the privileged control plane, and active operator turns
  cannot be contaminated by an automatically delivered bus turn.
- When neither a manager nor an independent Overseer can receive the request, the hub journals an explicit
  upstream-unavailable lifecycle event rather than pretending the prompt was delivered.
- In-process and detached-worker execution share provider-specific denial guidance. Claude is instructed not to
  replace a host permission with prose or `AskUserQuestion`; Codex receives the equivalent rule for
  `request_user_input`. Both report an exact delegated-work block upstream and continue safe work.
- Codex 0.145 `item/permissions/requestApproval` is no longer answered with the command/file approval
  `{ decision }` shape. On approval the hub returns exactly the requested permissions as a turn-scoped granted
  subset; on decline it returns an empty subset. This matches the generated installed app-server schema and
  avoids both silent rejection and accidental over-granting.

## Child purpose inspection

- Every managed child with a configured role/purpose gains a small information symbol beside its name in both
  the main sidebar and Project Overview team list.
- Hover and keyboard focus expose immediate purpose metadata; click opens a bounded popout with the full text.
- The control is independently focusable and labeled for assistive technology, supports Escape and blur closure,
  and suppresses row click, double-click, pointer, and drag propagation so inspection never opens, renames, or
  drags the child chat.
- The click popout uses viewport positioning so nested and scrollable team containers cannot clip long purposes.
