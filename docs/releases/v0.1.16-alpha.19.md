# AllMyAgents v0.1.16-alpha.19

Released 2026-08-04.

## Purpose

This release removes AllMyAgents remote control from the failure boundary of mapped AllMyStuff Sites.
Pairing, remote testbed operations, and Overseer-to-Overseer communication now use an authenticated
Site-free MyOwnMesh RPC lane. It also makes existing Application Overseers aware of the complete local
fleet and upgrades their durable conversations onto the expanded capability contract automatically.

The complete feature and fix log for the preceding cut remains in
`docs/releases/v0.1.15-alpha.18.md`; it includes the continuous-history, truthful-activity-clock, and first
Overseer migration work rather than reducing that release to a terse changelog entry.

## Site-free remote control

- The hub registers one versioned `allmyagents.hub.v1` method on MyOwnMesh's existing authenticated
  application RPC lane. It opens no second TCP listener and does not require a mapped localhost Site.
- The bridge discovers the real AllMyStuff fleet, excludes claim/support networks, exposes peer liveness
  and RTT, and keeps one bounded event subscription with reconnect/backoff for inbound calls.
- Remote capability discovery and approved file, terminal, environment, and WSL operations prefer the
  direct lane. Existing Site HTTP remains a mixed-version compatibility fallback.
- Once a mutating operation selects the direct lane, an ambiguous timeout or lost response is returned to
  the caller and is never replayed over Site HTTP. A write or shell command therefore cannot execute twice
  merely because its response was lost.
- Operation results retain route, target, network, round-trip, request/response byte, transfer-byte, and
  throughput evidence when observable. Failures remain classified as pairing, route, transport, timeout,
  protocol, or target failures.
- Direct RPC registration follows the operator's mesh-exposure switch. A disabled hub neither registers a
  handler nor attempts direct calls; runtime enable/disable starts and stops the bridge immediately.
- Blue/green restarts release the process-local RPC method only after blue has surrendered the public
  listener. Green claims it after promotion, and a rolled-back blue reclaims it with the listener.

## Reciprocal pairing and authentication

- Pairing now uses a short-lived, one-use eight-character code over the direct peer route. One successful
  exchange stores reciprocal hub capabilities, so the operator does not have to repeat pairing in the
  opposite direction.
- Pairing is bound to the cryptographically authenticated MyOwnMesh peer identity before the code is
  redeemed. Labels and identity lengths are bounded and control characters are rejected.
- Every post-pairing request is independently HMAC-SHA256 authenticated with a version, random message id,
  source identity, operation, payload, and five-minute timestamp window. Source identity must match the
  authenticated mesh peer.
- Connection-list and agent-facing APIs never disclose stored long-lived capabilities. Legacy device-token
  entry remains available only for an older peer whose Site route is still reachable.
- The new pairing control renders as eight individual accessible cells, inserts the separator after four
  characters, uppercases and sanitizes input, supports whole-code paste and keyboard navigation, and
  submits only when all eight characters are present.

## Remote-access visibility and recovery

- Remote access now has an explicit Refresh action. A manual refresh cannot be swallowed by an overlapping
  background poll; it waits for that poll and then performs its own forced route-discovery pass.
- The fleet model reports Site reachability separately from direct-control reachability, status, and RTT.
  A healthy direct peer no longer appears simply as `mesh route offline` when its mapped Site is dead.
- Direct-only peers can be paired and used as approved testbeds. The UI explains that the unified remote
  project/chat stream still needs the compatibility Site route in this release.
- Route diagnostics distinguish a missing/dead Site from a live direct lane and retain the most recent
  refresh timestamp and error in the Remote access panel.

## Overseer fleet control

- The Overseer capability-manifest version advances to 2. Existing durable Overseer sessions migrate in
  place after the hub owns the public role, preserving their session id, vendor conversation, transcript,
  and selected account while receiving the current live tools and regenerated instructions.
- `list_agents` gives the Overseer the complete local fleet, including stopped chats, project, role,
  provider, and status. Ordinary agents retain their same-project boundary.
- `peek_agent` gives the Overseer every read-only inspection view across the local fleet. Ordinary agents
  and managers retain their prior teammate/direct-child limits.
- A direct operator-origin Overseer turn may message an exact local chat across project boundaries. A
  teammate-, system-, or failure-alert-caused turn cannot inherit that authority.
- New Overseer operations list authenticated peer Overseers and send a bounded peer message over the
  direct lane. The receiving hub injects it as explicitly semi-trusted bus provenance, never as operator
  authorization.
- A peer-caused Overseer turn may reply only to the exact authenticated source hub. It cannot mutate local
  app state or address a different hub.
- External message receipts and bus fanout commit atomically and are bounded to the newest 10,000 receipts,
  making network retries exactly-once without creating another unbounded journal.

## Security and lifecycle invariants

- Direct actions still require three independent gates: reciprocal hub pairing, the target machine's
  disabled-by-default root/capability policy, and the source chat's exact operator-granted device scope.
- WSL roots stay distribution-specific. Environment inspection remains bounded and does not disclose
  environment variables or credentials; terminal permission remains whole-account shell authority rather
  than a filesystem sandbox.
- Remote peer messages are visibly framed with their hub identity and a warning that the content is not
  authorization for approvals, permission changes, restarts, elevated commands, or other mutations.
- Pairing, direct actions, connection changes, peer Overseer traffic, RPC lifecycle, and transport outcomes
  are journaled without file contents, command output, or stored credentials.

## Compatibility boundary

The direct lane in this release covers pairing, approved remote files/terminal/WSL testbeds, telemetry, and
Overseer-to-Overseer messages. The already-shipped unified remote project/chat viewer still uses each peer
hub's HTTP/WebSocket Site mapping. This is deliberate and stated in the UI: losing a Site no longer blocks
direct control, but it can still make that peer's live chat timeline unavailable until a later release moves
the multi-hub replay stream onto a gateway or stream-capable direct protocol.

  deduplication, source-only reply authority, and atomic external-bus receipts are covered.

  public listener closes.
