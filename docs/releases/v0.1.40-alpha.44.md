# AllMyAgents v0.1.40-alpha.44

Released 2026-09-04.

## Purpose

This release makes GPT-6 Astra available to the Codex accounts that actually have it, restores immediate operator
steering during active manager work, and gives remote builds a durable, fail-closed dependency setup path.

## Account-scoped GPT-6 Astra

- The bundled Codex client is updated from 0.145.0 to 0.153.3, whose live `model/list` surface advertises
  `gpt-6-astra` to entitled accounts.
- AllMyAgents continues to treat the provider's per-profile model catalog as the entitlement boundary. Astra is
  shown only for an account that advertises it; it is deliberately absent from the global fallback catalog.
- The picker carries the account's live model name, default selection, supported reasoning efforts, and service
  tiers. Current provider metadata includes low through ultra effort, medium as the default, and optional Fast.
- Existing account-only catalogs remain isolated. One account can expose Astra or Daybreak Blue without implying
  that any other local or fleet account can use those models.
- The shipped dependency, npm lock, pnpm lock, and diagnostic probe are pinned to Codex 0.153.3 so clean installs
  and packaged installs use the same app-server contract.

## Immediate operator steering

- A direct operator message sent while a teammate-origin manager turn is active is delivered through the
  provider's native steer operation immediately instead of waiting for the turn to end.
- The current turn is not promoted merely because text reached the HTTP endpoint. Operator authority begins only
  after the provider accepts the authenticated steer boundary, and that transition is journaled explicitly.
- If the turn becomes idle before the provider accepts the steer, the message is retained durably and delivered
  exactly once in a fresh operator-origin turn. Busy/idle races therefore cannot lose the instruction.
- Regression coverage exercises permission decisions on both sides of the accepted boundary and the exactly-once
  fallback path.

## Durable remote dependency setup

- `start_run` now accepts `required_tools` plus a project-reviewed `setup_command` for remote targets.
- The hub inspects the target first. When dependencies are missing, it starts setup as its own durable run with an
  independent id, logs, resource lease, timeout, provenance, and exact terminal state.
- The requested build remains queued behind that prerequisite. It begins only after setup succeeds and a second
  environment inspection proves every declared tool is present.
- Setup failure or incomplete provisioning fails the dependent run without executing its command. The hub never
  guesses packages, invents a second project manifest, or silently installs dependencies as an untracked side
  effect.
- Agent guidance now tells managers and the Overseer to use the project's reviewed bootstrap/Justfile/setup recipe
  when a target is missing declared tools.
