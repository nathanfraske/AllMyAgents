# AllMyAgents v0.1.24-alpha.28

Released 2026-08-10.

## Purpose

This release replaces ad-hoc agent-managed build locks and fragile shell waits with one provider-neutral durable
run control plane. Managers and the application Overseer can schedule important local or granted-remote work,
partition independent jobs across devices and resources, retain exact outcomes and logs, and query current team
state without polling every child or reading an unbounded journal.

It also carries every operator-facing fix landed after `v0.1.23-alpha.27`: stable hub connectivity indicators,
enforced manager task accounting, correction of the retired-agent restoration regression, and read-before-write
mesh exposure upkeep.

## Durable local and remote runs

- Claude and Codex receive the same `start_run`, `inspect_runs`, and `control_run` tool schemas through the shared
  AllMyAgents tool bridge. The hub, not the model, owns queueing, execution state, and authorization.
- Every run has an immutable ID, actor and target session, project, kind, local or remote target, bounded command
  summary, command digest, resources, creation/start/heartbeat/completion times, exact exit code or signal, and
  one terminal state: succeeded, failed, cancelled, or `outcome_unknown`.
- Local execution uses one executable plus an argument vector with `shell:false`. Remote execution retains the
  target device/root identity and routes through that target session's existing explicit terminal grant.
- Standard output and error are retained outside the journal with a 16 MiB cap per stream. Inspection returns at
  most 64 KiB per stream and explicit byte cursors, so a manager can follow a large build without repeatedly
  materializing its whole log.
- Remote results retain route, network, target and round-trip timing, transfer counts, failure stage, timeout state,
  and the target correlation ID when the remote transport supplies them.

## Parallel placement and resource leases

- The target checkout or remote physical root is always leased. Callers may add project-scoped resources such as
  `gpu-0`, `port-8080`, a test fixture, or another exclusive device.
- Runs whose resources do not overlap start concurrently. A manager can therefore split a build/test matrix across
  separate remote devices or roots, or use multiple local worktrees without inventing lock files.
- Runs sharing any resource remain queued until the owner reaches a terminal boundary. The claim and run-state
  transition are one SQLite transaction, including the loser path when two hub owners race to claim work.
- The target-side physical-root fence remains authoritative across source hubs. Generic durable runs do not create
  duplicate legacy testbed-run records; compatibility callers using `remote_exec` continue to use the older ledger.

## Provenance and crash truthfulness

- A run records the local source checkout's Git HEAD and branch when available, hashes for every changed and
  untracked source input, lockfile hashes, and a digest of the effective allowlisted environment.
- Provenance scanning is asynchronous and bounded at 10,000 files and 512 MiB. Exceeding the boundary records
  `complete:false`; it never blocks the hub event loop indefinitely or pretends a partial manifest is exact.
- Environment values are not copied into lifecycle journal events. Remote runs label the captured environment as
  source-hub context rather than falsely claiming it describes the remote shell.
- Active runs heartbeat their claims. A promoted hub owner leaves fresh predecessor work alone and changes only a
  stale unobserved run to `outcome_unknown`, releasing its scheduling claim without claiming success, failure, or
  cancellation. Agents are explicitly told never to retry that state blindly.
- Queued and running local work can be cancelled. A running remote request is not falsely reported cancelled:
  remote live cancellation remains unavailable until the target protocol can prove termination.

## Bounded operational team query

- `query_team` provides one non-destructive view across selected team messages, task boards, pending approvals,
  and durable runs.
- Manager scope is derived from the authenticated manager hierarchy. An Overseer can inspect non-retired records
  on its own hub, but must pass explicit session IDs when a fleet-wide selection would exceed 64 active records.
- Message filters execute in SQLite before materialization. Pages use append-only row IDs as stable cursors,
  return `hasMore`, and never mark the underlying messages delivered or read.
- Session, sender, status, kind, unread, and limit filters let a supervisor ask for the exact pending slice rather
  than combining unbounded `read_messages`, per-child peeks, approval polling, and retained sequence IDs.

## Claude, Codex, manager, and Overseer methodology

- Both providers receive the same authorization and run/query contracts. Provider-specific text only explains the
  correct native discovery path; it does not change the available authority.
- Existing Overseers migrate to capability contract v14 and existing managers to team contract v4 on the next
  public-owner boot. Rematerialization is idempotent, does not create a turn, and does not append recurring mail.
- Managers are told to begin every operator task or material slice with a bounded operational query, maintain their
  own provider-native plan, assign every direct worker an exact durable task, dispatch useful parallel lanes up to
  their configured staffing target, and reconcile ownership before reporting.
- Important builds, tests, lints, benchmarks, and deploys use durable runs. Instructions explain how distinct
  checkout/root/GPU/port keys create parallel lanes and how shared keys deliberately serialize them.
- A direct Full Access turn or an exact operator remembered `start_run` grant can approve the execution class.
  Teammate-caused turns remain denied by default, preserving the existing origin and blast-radius boundary.

## Included post-alpha.27 fixes

### Hub connectivity stability

- The renderer no longer treats a brief health-probe or reconnect gap as a new outage on every sample. A live
  connection remains authoritative through the bounded gap, preventing fleet rows from flickering between healthy
  and error while the hub is still present.
- Regression coverage exercises the outage/recovery hysteresis and ensures a genuine sustained failure still
  becomes visible.

### Manager task accountability

- Managers receive a standing requirement to create or update their own provider-native coordination plan, call
  `assign_child_task` for each exact worker outcome, retain returned task IDs, and update the same assignment only
  on a real state transition.
- Progress and completion reports must reconcile every involved manager-owned assignment. “No tasks reported” is
  explicitly treated as missing accounting rather than evidence that an agent has no work.

### Retired-agent archive correction

- Records retired before the capability-v2 migration remain in the project archive instead of being restored into
  the active roster. Untouched migration victims are re-archived, while an agent genuinely used after that migration
  remains active.
- Archived records retain identity, transcript, attribution, role, team and reversible restoration evidence, but
  do not appear in the live catalog or consume active team counts and caps.

### Idempotent mesh exposure

- Automatic AllMyStuff/MyOwnMesh upkeep reads the current exposure map and performs no write when `tcp:7777` is
  already advertised correctly.
- Overlapping registration callers share one in-flight attempt. This eliminates the 30-second profile-restamp and
  backend inventory loop that caused needless CPU, PowerShell/WMI work, command-window churn, and latency jitter.

## Known boundaries

- Run processes are durably observed and recoverable, but are not yet detached job objects guaranteed to survive a
  hub process replacement. An unobserved stale command becomes `outcome_unknown` rather than fabricated success.
- Running remote cancellation remains intentionally unavailable until the remote node can acknowledge and prove
  process-tree termination.
- Remote provenance currently captures exact source-hub inputs and returned target telemetry. A future target
  protocol can add independently attested remote environment and artifact manifests without changing run IDs or
  scheduler semantics.

## Updating

Existing installs can use **Settings → Check for updates** after the signed release assets are published. The
GitHub release provides Windows MSI/NSIS and Apple Silicon/Intel macOS downloads. Windows SmartScreen and macOS
notarization warnings retain the documented alpha behavior; updater signatures and release checksums remain the
integrity boundary.
