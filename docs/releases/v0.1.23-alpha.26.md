# AllMyAgents v0.1.23-alpha.26

Released 2026-08-09.

## Purpose

This release turns the remote-device prototype into a project-aware testbed control plane, makes manager teams
durable and deliberately parallel, adds bounded remembered child approvals, and fixes the intermittent blank
transcript caused by large-journal maintenance pauses.

It also corrects the dashboard's activity and usage labels. The preceding cut's complete feature and fix log is
preserved in [`v0.1.22-alpha.25.md`](v0.1.22-alpha.25.md); this document records every operator-facing change
since that tag.

## Project-aware remote testbeds

- Projects now own a durable location registry with one canonical local primary and optional attached remote
  checkouts. WSL locations retain their distribution and Linux-native path as part of the identity.
- Project Overview shows location readiness, remote environment, repository state, active reservation, latest
  attributed run, and preparation state without turning a location record into an authority grant.
- Remote terminal runs receive a durable run id only when project membership, attached location, and the chat's
  explicit root/terminal grant all agree. The ledger records immutable agent/session and account attribution,
  command digest and bounded summary, base revision, telemetry, result, exit code, and exact failure stage.
- Source-hub reservations and target-root execution locks prevent two agents or hubs from mutating the same
  testbed concurrently. A source restart closes its own unfinished run as an unknown/cancelled outcome instead
  of inventing success.
- A fixed-argument Git inspection reports bounded HEAD/ref, dirty state, and credential-free origin identity.
  It does not fetch, mutate the checkout, expose remote URLs, or treat truncated output as clean.
- **Prepare** converges an existing attached checkout to the primary's exact clean, published commit. The hub
  derives every Git argument, verifies repository identity and the advertised branch/commit, disables hooks and
  external remote helpers, leases the location, checks out detached, and verifies the result. It refuses dirty,
  detached, unpublished, mismatched, incomplete, or busy locations and never resets, cleans, or stashes.
- Agents with the same explicit project/root terminal grant can use `remote_prepare_project_location`; the
  browser and model cannot supply an arbitrary ref, commit, repository, or path.

## Lightweight fleet testbed nodes

- The release carries a checksum-manifested, dependency-free testbed payload for its own OS and architecture.
  A target needs AllMyStuff/MyOwnMesh file and terminal planes, but no AllMyAgents UI, journal, Overseer, Claude
  account, or Codex account.
- On a direct operator turn, the Overseer can discover signed-fleet targets, inspect their observed platform,
  explain the selected privilege profile and blast radius, transfer the exact bundled payload, verify every
  SHA-256, install it, wait for registration, probe it, and clean the unique bootstrap directory.
- Windows `elevated-machine` installs a highest-privilege LocalSystem startup task. Linux `elevated-machine`
  installs a root systemd service. Linux `linux-sudo-machine` creates a dedicated account with an explicitly
  validated `NOPASSWD: ALL` sudoers entry. These are opt-in machine-administrator profiles, not implied by a
  chat's Full Access setting.
- Deployment never transfers vendor credentials or creates a target Overseer. Same-fleet identity admits the
  source hub to the node, while each agent still requires an explicit device/root/capability grant.
- Ambiguous install/transport outcomes are not retried. Transfer and install results retain byte counts,
  throughput, elapsed time, route timing, failure stage, and cleanup state.
- Automatic cross-architecture deployment remains bounded by the release payloads actually carried by the
  source install. A Windows/x64 build cannot masquerade as a Linux/ARM64 installer.

## Direct agent methodology for remote work

- Claude and Codex Overseers, managers, workers, and ordinary chats receive the same provider-native remote
  workflow on every turn and after compaction: list granted devices, ping, inspect environment, inspect Git,
  prepare only an attached checkout when needed, then use bounded files or terminal tools.
- Guidance requires agents to surface latency, transfer progress, throughput, and exact failure stages, and to
  avoid blindly repeating an ambiguous write, preparation, or command.
- The Overseer receives the dedicated target-discovery and deployment workflow, including the difference between
  a full remote hub and a vendor-free headless node.

## Durable manager teams and deliberate parallelism

- Managers no longer manufacture a new retired roster as ordinary tasks finish. Durable workers retain their
  identity, role, transcript, culture, worktree, and relevant context across assignments and provider compaction.
- Every manager-created worker requires either an operator-defined `agent_type` or an explicit durable role.
  Account selection alone cannot create an identity-less generic child.
- `manage_team` now treats a lineup switch as a durable stash/activate operation. The outgoing team's sessions,
  branches, dirty files, and history remain intact; a running team cannot be shelved without explicit interrupt.
- Managers can resume stopped/errored workers and repair legacy roles. Retirement remains only a compatibility
  escape hatch for old records; new routine retirement is disabled.
- Each manager has a bounded parallel staffing target, defaulting to three useful direct lanes and capped by its
  live-child ceiling. At every new task or material slice it must reassess independent implementation, research,
  reproduction, and cross-check lanes, while explaining a real dependency when fewer lanes are useful. Guidance
  explicitly forbids invented, duplicated, or prolonged work merely to fill capacity.
- Project creation/edit flows and Overseer setup carry the staffing target and durable role definitions through
  both providers.

## Remembered manager approvals

- `decide_child_approval` can now approve once or use `remember=true` for the exact recognized ordinary tool or
  Git action class on one direct worker. Future matching calls auto-approve without manager micromanagement.
- A remembered rule is stored as the worker's existing durable delegated grant, survives restart/compaction,
  is rechecked against the manager's live operator ceiling on every use, and remains revocable immediately with
  `set_child_authority`.
- The grant, each later use, revocation, and originating approval are journaled. It cannot exceed the operator's
  manager toggle, validated hierarchy, Git boundary, tool allowlist, or permission-mode ceiling.
- `remember=true` is rejected for denials and one-shot descendants. One-shot workers inherit the direct worker's
  grant, preventing a disposable nested chat from becoming a new standing-policy scope.
- Manager prompts distinguish recurring understood actions from unusual or high-blast-radius work, which should
  remain one-time approvals.

## Large-journal transcript and maintenance reliability

- Live diagnosis on the operator's 1,770,860,544-byte journal showed the latest-history SQL completing in about
  two milliseconds while `/api/health` paused for 10.5 seconds. The blank transcript was therefore not an
  unindexed history query: periodic maintenance held SQLite's single writer lock while the hub's synchronous
  append waited in native code, freezing HTTP and WebSocket work past the renderer's eight-second deadline.
- Condensation moves the oversized-row diagnostic outside the write transaction and replaces four payload-table
  delete passes with one bounded primary-key delete. The selected kind counts come from the compact transient
  projection and the transaction verifies the exact deleted-row count before commit.
- Maintenance logs the measured writer-lock duration so future regressions are observable rather than inferred
  from renderer timeouts.
- Full online backup, integrity verification, hashing, and recovery-generation publication now run in a dedicated
  child process. The hub still owns scheduling, lease/epoch control, progress, result, and fail-closed publication,
  but synchronous SQLite and filesystem verification no longer occupy its HTTP/WebSocket event loop.
- Latest and older native/imported transcript reads retry one transient timeout with a fresh abort signal and a
  bounded 20-second recovery window. Real HTTP/generation failures remain visible, and an explicit **Retry
  history** control prevents a failed first read from leaving an unrecoverable empty pane.

## Dashboard and usage truthfulness

- Heatmap intensity is now relative to the busiest day in the visible window instead of a nearly binary
  worked/did-not-work color. Low-activity days stay visible while materially busier days are visibly stronger.
- The monetary aggregate is labeled and computed as Claude **API-equivalent estimate**, not subscription spend
  or a provider invoice. Codex subscription turns do not fabricate a per-turn dollar amount.
- Usage resets more than 24 hours away render as an absolute local time and date (for example,
  `Resets 4:00 PM Sep. 7th`). Under 24 hours they switch to a live Claude-style hours/minutes countdown.
- Project/team totals count only live roster members. Archived/retired records remain inspectable evidence but do
  not consume active counts or caps.

## Elevation boundary

- The desktop app still does **not** install a resident privileged local command broker. Local elevation remains
  the existing audited one-shot Windows UAC child, so installing the ordinary per-user desktop app once does not
  create a permanent SYSTEM shell.
- Persistently elevated execution is available only on an explicitly deployed testbed node through the named
  privilege profiles above, plus the agent's separate durable device/root/terminal grant. A future desktop broker
  would require authenticated ACL-restricted IPC, replay protection, exact command digests, narrow policy,
  path containment, complete audit, and protected service update/removal before it could be safe to ship.

## Known boundaries

- This workstation does not hold the protected updater private key. The tag workflow rebuilds, signs, and
  publishes updater artifacts after the exact-tag Windows/macOS durability gates pass.
- The release provides project-aware remote execution and attribution, not VM/container isolation or CPU/GPU/RAM
  quotas. A terminal grant runs with the target service account's OS authority.
- Cross-device project locations currently converge an existing clean published checkout. Cloning an absent
  checkout, transferring dirty work, live resource accounting, result ingestion, and crash-surviving job objects
  remain later protocol layers.
- macOS installed-launch behavior and the updater round-trip retain the documented alpha limitations in
  [`alpha-cut-checklist.md`](../alpha-cut-checklist.md).

## Updating

Existing installs can use **Settings → Check for updates** after the signed release assets are published. The
GitHub release also provides Windows MSI/NSIS and Apple Silicon/Intel macOS downloads. Windows SmartScreen and
macOS notarization warnings may still appear during the alpha; updater signatures and release checksums remain the
integrity boundary for this cut.
