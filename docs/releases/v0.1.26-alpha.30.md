# AllMyAgents v0.1.26-alpha.30

Released 2026-08-13.

## Purpose

This release consolidates the application around a smaller set of understandable control surfaces and removes
several recurring sources of manager stalls: provider-shaped permission ceilings, lossy approvals, stale account
facts, invisible usage exhaustion, and live configuration copied into prose. It also adds a single device overview
for hubs and lightweight testbeds and makes direct-mesh failures diagnosable instead of presenting every failure as
an unexplained offline route.

## Simplified settings, projects, and devices

- Settings is organized into task-oriented sections with descriptions and a visible saving, saved, or failed state.
  Application preferences are persisted by the hub and survive restarts and updates, including explicit `false`
  values that the former merge path could accidentally discard.
- Project editing is grouped into General, Team & manager, and Automation. The ordinary project-removal path and the
  destructive project-and-files path remain distinct, but are now reachable from one project settings surface.
- A connected-device overview lists local and remote hubs, lightweight testbeds, grants, roots, online state,
  operating system, architecture, CPU and memory observations, and available file/terminal capabilities. The view
  explains which records are control-plane hubs and which are execution-only testbeds.
- Remote peer Overseers no longer fall into the local Unfiled chat catalog. Overseer ownership remains hub-local;
  remote hubs and their health belong in the device overview rather than masquerading as local chats.
- Operator questions are first-class notifications. The Overseer now has an action-required indication when it needs
  an answer, alongside approvals, failures, stalls, completions, and journal pressure.
- A history-generation transition no longer erases the already-rendered live tail. The renderer retries a transient
  generation change and retains a manual retry path when the journal cannot supply the older page yet.

## Provider-neutral manager capabilities

- Manager ceilings now use semantic capabilities: `shell`, `file_write`, `file_read`, `web`, `browser`, and `runs`.
  The hub resolves those grants to Claude Bash/Edit/Write tools, Codex commandExecution/fileChange tools, and the
  matching AllMyAgents tools at decision time.
- Existing provider-specific grants migrate idempotently. Unknown plugin or MCP tool names retain exact-match
  semantics, so the migration does not silently broaden third-party capabilities.
- Narrowing a ceiling immediately intersects every live child grant with the new semantic boundary. Revocation is
  effective on the next action, not merely the next chat or app restart.
- Cross-provider regressions prove that one `shell` grant permits the same bounded shell action for a Claude worker
  and a Codex worker, while unrelated and unknown actions continue to ask.

## Durable approval lifecycle

- Human-facing approvals default to one hour instead of expiring after ten minutes. Operators can set
  `approvals.timeoutMinutes` from 1 minute through 24 hours for their deployment.
- A timeout is a distinct terminal outcome from a denial. Workers receive `timeout`, can report that nobody answered,
  and no longer have to infer that the operator deliberately refused the request.
- Changes to manager ceilings, child exact grants, allowed accounts, or bounded GitHub automation deterministically
  re-evaluate affected pending approvals. Every automatic release has a journal event and the corresponding stale
  inbox/bus notification is marked resolved.
- Re-evaluation preserves the delegation invariant: widening the manager's ceiling alone is not a standing child
  permission. A pending action releases only when the live child grant and the manager ceiling both cover it.
- Expired requests remain audited and are re-notified as expired rather than silently disappearing. Resolved approval
  alerts are no longer delivered as if they were still awaiting attention.

## Account health, usage headroom, and balanced placement

- Authentication, provider entitlement, and usage capacity are separate states. A valid OAuth credential rejected
  with an organization entitlement error is shown as authenticated but not entitled instead of as healthy or logged
  out.
- Provider rate-limit events and usage windows feed a persistent per-account ledger containing entitlement,
  limit status, window type, estimated headroom, and reset time. The Overseer status and account/manager UI use the
  same projection after hub restarts.
- Provider rejection is authoritative. New sends, spawns, and team launches fail fast on an exhausted or unentitled
  account rather than creating a succession of agents that each die independently.
- Usage-aware agent roles can name several candidate accounts. The hub chooses the eligible account with the most
  headroom using a deterministic tie break and journals the selection rationale.
- Independence groups preserve structural review boundaries: balancing cannot place an implementer and the reviewer
  constrained against it on the same account merely because that account has more remaining capacity.
- A fully blocked lineup returns one preflight error and creates zero managers or workers. Capacity alerts are
  coalesced per account/window and include the reset time when known.
- The app does not burn provider tokens on a synthetic periodic entitlement probe. Entitlement begins as unknown and
  is upgraded or denied only from real provider execution telemetry; this avoids turning health monitoring into a
  hidden usage source.

## Live generated manager state and compaction continuity

- Every manager turn receives a bounded, machine-generated block derived from current configuration: allowed
  accounts and health, role-to-account/model/effort mapping, live child names and statuses, semantic tool ceiling,
  Git authority, active/stashed team state, task accounting, and bounded operator-intervention provenance.
- Generated configuration is authoritative over old prose. Editable orientation, standing instructions, and operator
  tasks carry intent; they no longer need to remember account assignments or copy a frozen roster.
- Prose that restates profile IDs is flagged to the operator as likely configuration drift. Operator tasks carry an
  update timestamp and the project UI warns when they are older than seven days.
- The first orientation message is sent once and is no longer duplicated inside a second saved starting prompt.
  After compaction, the live block is regenerated rather than summarized or recovered from stale conversation text.
- Existing managers migrate to team capability manifest v5 in place. Their transcript, identity, roles, teams, and
  worktrees remain intact; instructions rematerialize once without waking the chat or creating reminder loops.
- Claude and Codex receive the same task-accountability, parallel staffing, provider/tool discovery, and compaction
  continuity contract through their supported native instruction paths.

## Team launch and operator-origin correctness

- Launching a saved team onto a project that already has a project manager now fails clearly instead of silently
  creating a second manager.
- A manager-spawned child uses the configured agent-type display name and durable role, matching team-preset launches
  and keeping the live roster joinable to saved configuration.
- Operator input arriving during a non-operator turn remains safe: it does not silently upgrade that turn's mutation
  authority. Both the agent and UI now receive an explicit notice explaining that the instruction must be resent when
  the chat is idle if direct operator authority is required.
- A worker handoff that the hub could not confirm is classified as an infrastructure interruption with an unknown
  outcome, not as an agent failure. The chat returns to an operable state and the app does not blindly retry a command
  that may already have started.

## Direct mesh diagnostics

- MyOwnMesh control errors are no longer swallowed into a bare `available:false`. Direct RPC reports one of:
  connecting, daemon absent, permission denied, no eligible network, or control error, with a bounded remediation
  message in the Remote settings surface and hub log.
- Windows permission denial specifically explains that the elevated MyOwnMesh control pipe must grant the interactive
  user full-duplex access. This identifies the observed cause of fleet auto-link failure instead of asking the operator
  to recreate pairing codes repeatedly.
- Site/manual pairing remains a compatibility fallback while direct RPC is unavailable; the UI no longer presents it
  as the preferred route when the signed fleet plane should be usable.

## Known boundaries

- The MyOwnMesh pipe ACL is created by the separate MyOwnMesh daemon and cannot be repaired from this repository.
  This release detects and explains that failure. The daemon must grant the interactive user read/write access, using
  the existing AllMyStuff node pipe ACL pattern, before direct-RPC fleet auto-link can become available.
- Usage headroom is exact when the provider supplies a rejection or used-percent window. Otherwise it is a bounded
  estimate used to rank eligible accounts, never a claim about billing or remaining token cost.
- Operator-origin safety still binds privileged mutations to a direct operator turn. A visible mid-turn notice fixes
  the silent failure mode without allowing teammate or alert turns to acquire operator authority.

## Updating

Existing installs can use **Settings → Check for updates** after the signed assets are published. The GitHub release
provides Windows MSI/NSIS and Apple Silicon/Intel macOS downloads. First run requires internet access while the bundled
runtime installs its locked vendor dependencies.

For macOS, the supported alpha install command is:

```sh
curl -fsSL https://raw.githubusercontent.com/nathanfraske/AllMyAgents/main/scripts/install-macos.sh | bash
```

Windows SmartScreen and macOS notarization warnings retain the documented alpha behavior.
