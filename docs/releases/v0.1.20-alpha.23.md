# AllMyAgents v0.1.20-alpha.23

Released 2026-08-05.

## Purpose

This release gives the operator a durable way to pre-authorize a deliberately narrow set of GitHub
operations for a project or one exact chat. Managers and their teams can now create and maintain pull
requests, merge explicitly identified pull requests, run explicitly identified workflows, and push an
explicit branch to the project's canonical `origin` when—and only when—the operator granted the matching
capability.

This is not a blanket Bash, PowerShell, Git, or GitHub CLI exemption. Full Access continues to describe the
agent's local execution posture; GitHub automation remains a separate, inspectable policy with a closed
classifier and a normal approval fallback for anything outside its bounds.

The provider continuity, compaction, upstream approval routing, journal recovery, lazy history, account
sign-in, project lifecycle, remote testbed, team generation, workspace reclamation, and supervisor hardening
from prior cuts remains documented in the earlier release ledgers. This document records the additional
release delta.

## Durable project and exact-chat policies

- A project can grant GitHub automation to its current and future managers, workers, and teams. Because the
  grant belongs to the project rather than a transient manager session, it follows deliberate manager and
  team rotations without having to recreate the policy for every replacement agent.
- An exact-chat grant can instead target one manager, worker, scratchpad, or Application Overseer. It does not
  leak to siblings, future sessions, or other projects.
- Four capabilities are independently configurable:
  - pull-request work;
  - pull-request merges;
  - workflow runs;
  - repository pushes.
- The existing permission picker exposes the exact-chat controls, while Project Settings exposes the durable
  project controls and explains which sessions inherit them.
- Authenticated API clients can read or update either scope. The hub validates capability names and target
  identity rather than accepting an arbitrary policy blob.
- Every change is committed to SQLite and journaled in the same transaction, including actor, scope, target,
  resulting capabilities, and timestamp. Every automatic use is journaled with the matched capability and
  bounded operation evidence.

## One approval boundary for Claude and Codex

- Claude Bash requests and Codex command-execution approval payloads reach the same GitHub automation
  decision point. The classifier therefore cannot silently diverge by vendor or execution transport.
- An eligible manager or managed child may use project policy while working from an authenticated manager or
  bus-origin assignment; a delegated task no longer becomes unusable merely because the operator did not type
  the immediate turn.
- The Application Overseer remains more restrictive: an Overseer GitHub operation is eligible only during a
  positively identified direct-operator turn. A teammate, project manager, remote peer, or system message
  cannot borrow the Overseer's authority.
- A match only auto-approves that one request. The agent's general permission mode is not rewritten and the
  shell tool is not added to a durable “always allow everything” list.
- Any ambiguous, malformed, unsupported, or excessive request falls back to the existing operator approval
  flow with its original evidence intact.

## Closed operation classifier

The classifier recognizes a small, auditable command language rather than trying to prove that arbitrary shell
text is safe. Supported operations are restricted to noninteractive `gh pr` work, explicit `gh workflow run`
or `gh run` operations, and explicit one-ref `git push origin` operations covered by the selected capabilities.

It rejects and prompts for, among other things:

- shell chaining, substitution, redirection, command wrapping, and unknown executables or verbs;
- `gh api`, authentication, secrets, repository administration, and workflow enable/disable;
- admin merges, branch deletion, interactive CLI forms, and file upload/download convenience flags;
- `gh pr create` without an explicit head branch and noninteractive title/body or fill input;
- repository selectors that conflict with or escape the current project repository;
- executables that merely look like `gh` or `git`, alternate push URLs, non-`origin` destinations, force,
  delete, mirror, prune, wildcard, multi-ref, or implicit-current-branch pushes;
- repository-controlled Git execution settings and repositories with active or custom Git hooks.

For pull-request creation, the explicit `--head` requirement is material: current GitHub CLI documentation
states that it skips the command's otherwise implicit push/fork behavior. Each repository push must separately
name a single source branch and destination branch on literal `origin`, so the recorded policy matches the
actual remote mutation.

## Overseer capability contract v5

- The Overseer control surface gains `get_github_automation_policy` and `configure_github_automation`.
- Provider-native instructions teach both Claude and Codex when to inspect policy, how to present the four
  bounded choices to the operator, and that only a direct operator turn may configure or consume Overseer
  GitHub authority.
- Existing durable Overseer sessions migrate in place from capability contract v4 to v5. Their account,
  session identity, history, and active work remain intact; restart, resume, or compaction rematerializes the
  current tool contract rather than relying on remembered inventory.
- Policy configuration does not let the Overseer manufacture operator provenance, widen another agent's local
  grant, or approve a command outside the closed classifier.

## Security and durability invariants

- Policy is deny-by-default. An absent row, disabled capability, unknown scope, missing project association,
  stale session identity, or unprovable operator origin cannot auto-approve.
- Project matching is based on the hub's canonical project repository identity. User-controlled command text
  cannot select an unrelated repository and inherit the current project's policy.
- Durable policy reads and writes are bound to authenticated routes and existing operator/Overseer authority
  checks. The renderer cannot bypass the hub by mutating local state.
- Journal records contain the bounded decision evidence needed to explain why an operation was allowed without
  persisting credentials or raw secret material.
- Existing approval escalation remains the safety valve: a useful operation outside the policy is still
  possible after explicit operator review rather than being permanently forbidden.

## Updating

Existing installs can use **Settings → Check for updates** after the signed release assets are published. The
GitHub release also provides direct Windows MSI/NSIS and Apple Silicon/Intel macOS downloads. Windows SmartScreen
and macOS notarization warnings may still appear during the alpha; updater signatures and release checksums are
the integrity boundary for this cut.
