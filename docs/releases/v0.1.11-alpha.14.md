# AllMyAgents v0.1.11-alpha.14

Released 2026-08-01.

## Highlights

- Fixed a live Claude turn that remained permanently **active** after the vendor had already returned
  `terminal_reason: "aborted_streaming"`. Interrupt, Stop, later input, and repeated tab interaction could
  not recover it because the worker never emitted its terminal lifecycle message.
- Replaced the incorrect assumption that Claude emits one top-level result for every streamed user or steer
  message. The live journal proved that four accepted inputs can legally coalesce into one result.
- Preserved the permission-stream fix from the prior cut: a real queued continuation still keeps stdin open
  when its next SDK run starts, so mid-turn steering does not recreate the transient
  `Tool permission request failed: AbortError: Stream closed` cascade.
- Made **Always allow _tool_ in this chat** a real chat-wide operator grant. It now applies immediately to
  manager- and teammate-started turns instead of persisting successfully and then being ignored by the
  turn-origin clamp.

## Claude frozen-turn root cause and fix

The Claude adapter kept one streaming stdin/control channel open for a turn so the operator could steer it
at a tool boundary. The previous implementation counted accepted user messages and waited for an equal
number of top-level `result` messages before closing the stream. That model does not match the real SDK:
several priority-next inputs may be folded into one run and produce one result.

In the captured incident, the project-manager turn accepted its initial prompt and three operator steers,
then emitted one successful result. Since the counters could never become equal, the adapter kept the query
open. Later manager/bus traffic and another operator steer reused that false-live query. Interrupt produced
`aborted_tools` followed by the explicit terminal `aborted_streaming` result, but the same counter still
prevented stdin from closing. The vendor process was effectively idle while the worker and persisted session
continued to report `active`.

The adapter now uses a bounded result-boundary state machine:

- A result starts a one-second local quiescence window.
- A following `system/init` proves an already-accepted continuation became a new SDK run and cancels that
  close; the continuation receives the same intact permission/control channel.
- A quiet result boundary closes stdin and lets the query emit `turnCompleted`, returning the chat to idle.
- `terminal_reason: "aborted_streaming"` closes immediately because the SDK has explicitly declared the
  stream terminal.

This fixes both sides of the race: it neither closes underneath a real continuation nor waits forever for a
one-result-per-message relationship the SDK does not guarantee.

## Approval and Full access behavior

The approval service already persisted per-chat tool grants and consulted the live session record on every
tool call. However, the policy checked turn provenance first. A turn started by a manager or teammate was
rejected by that clamp before the policy ever reached `allowedTools`, so clicking **Always allow** produced a
success note and a durable grant that appeared to do nothing.

Standing tool grants are now evaluated before the mode-origin clamp, after all safety classification:

- only known ordinary execution approval kinds are eligible;
- interactive tools such as `AskUserQuestion` and `ExitPlanMode` remain ineligible;
- a vendor/user-authored `permissions.ask` rule still forces an operator prompt;
- capability-widening requests, practices, and unknown future approval kinds remain gated;
- revoking the tool in the permission popout takes effect on the next call.

Full permission mode retains its safer default provenance rule: turns directly started by the operator use
the selected mode, while teammate-started/unknown-origin turns remain clamped unless the operator explicitly
enables **Apply a chat's permission mode to turns it didn't start** in Settings → Danger Zone. The standing
per-tool grant is narrower and now means what its own label promises across the chat.

## Safety and compatibility

- No journal, account, project, session, credential, or worktree data is rewritten by this update.
- Existing per-chat allowed-tool grants remain compatible and begin using their documented chat-wide
  semantics immediately after the update.
- The updater version advances from 0.1.10 to 0.1.11 so installed clients can discover this cut.
- This remains alpha software. Windows installers are not Authenticode-signed, and macOS bundles are not
  notarized.
