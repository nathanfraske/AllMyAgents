# AllMyAgents v0.1.32-alpha.36

Released 2026-08-20.

## Purpose

This release makes child approvals usable when a Codex manager shares its account and checkout with workers,
provides an optional fast approval assistant for large teams, and treats private/preview Codex model access as an
account property rather than a global product assumption.

## Exact request-bound manager attribution

- Codex does not provide a thread id to its stdio MCP child. A manager and worker using the same account and
  checkout can therefore be indistinguishable by profile and working directory while both are active.
- `decide_child_approval` now uses the pending approval id as a second hub-issued attribution handle. The hub
  selects a manager only when exactly one matching project manager owns that requester through the durable
  hierarchy, has operator permission to decide child approvals, and covers the exact request with its live
  capability ceiling.
- This exception applies only to the one decision tool and one pending request. Unrelated calls under the same
  profile/cwd ambiguity still return **Not attributed**, so the repair does not turn a shared checkout into general
  manager authority.

## Hidden Manager Helper

- Project Manager settings can enable a helper account/model, low effort by default, and a maximum automatic risk
  of **low** or **medium**. Saved team presets retain the choice and launch validation checks the helper account
  before creating a team.
- Each approval is serialized through one helper lane per manager. The model receives one bounded request, current
  task and role context, and a deterministic risk floor; it returns one JSON decision and then exits.
- The helper cannot lower the deterministic risk floor. High/critical requests, requests outside the manager's
  operator-granted capability ceiling, uncertainty, malformed output, timeout, provider failure, sign-out, or
  entitlement loss remain pending and wake the real manager.
- Before applying an allow or deny, the hub rechecks that the approval is still pending and that the live manager,
  hierarchy, and operator ceiling still cover it. A concurrent revocation therefore wins.
- Provider execution uses a fresh temporary profile and empty workspace. Only the chosen account credentials and
  bounded model catalog are copied; project trust, MCP servers, hooks, plugins, skills, memories, browser/computer
  access, shell tools, and writable workspaces are absent. Claude tools are denied, while Codex runs read-only with
  approval policy `never`.
- Approved, denied, and escalated outcomes are journaled on the requesting worker and render as compact expandable
  cards showing risk, action, rationale, model, and approval id. The helper is intentionally not a tab or chat.

## Per-account Codex and Cyber model discovery

- The hub reads the bounded display/options projection of each profile's provider-maintained `models_cache.json`.
  It exposes slug, display name, description, supported reasoning efforts, service tiers, default effort, and
  default marker—never provider instructions or other large internal fields.
- Account catalogs replace the static Codex picker only for that account. A model unavailable to Codex B/C cannot
  become selectable there merely because Codex A advertises it.
- On the operator's current profiles, Codex A advertises `gpt-daybreak-blue-latest` (**Daybreak Blue**) with its
  supported effort levels, while Codex B and Codex C do not. The UI therefore exposes it precisely on Codex A.
- Missing, malformed, or concurrently refreshed caches fall back to the bounded static catalog rather than making
  profile discovery or app startup fail.
